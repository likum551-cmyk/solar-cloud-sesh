# GAGE-MP project lessons

- 2026-11-01: the Epic "UNABLE TO LAUNCH GAME" fix only worked from build\win\bin because it lived in that folder's hand-written gage_mp.cfg (epic_launch_url); the installer ships no cfg (and [InstallDelete] wipes it), so 0.3.1 fell back to a bare PlayGTAV and Epic's dialog came back -> a fix proven from build\win\bin is not shipped until it works with NO gage_mp.cfg: put defaults in code (now EpicLaunchUrl's built-in GTA V Legacy catalog ids), and test the installed copy, not bin.

- 2026-11-01: a "run every selftest" loop over `build/win/selftest/*.exe` also ran `gage_v.exe` (the devtool inject-chain harness, built into that folder). It tried to launch GTA ("Access is denied", so nothing started) and overwrote the HKCU\Software\GAGE-MP handoff (install_dir -> selftest\, server_host -> 127.0.0.1) -> run the selftests by explicit name (the list in CLAUDE.md), never by glob. If gage_v runs anyway, the next launcher Play rewrites those values.

- 2026-10-24: launching a freshly built GAGE-MP.exe (even a copy in another folder) while the owner's instance runs only signals that instance to show its window and exits 0 (single instance is machine-wide; gage.log: "another instance is running"), and a running build\win\bin\GAGE-MP.exe blocks the link with "Permission denied" -> before any exe run or link, list GAGE-MP.exe processes read-only; if one is not yours, rename the locked exe aside (a running image can be renamed) to link, and ask the owner to close theirs before a live run instead of launching into it.
- 2026-10-29: (a) a mingw/ninja build under the long agent scratchpad path failed with "opening dependency file ...: No such file" (object paths past MAX_PATH): build scratch trees under a short path such as %TEMP%\x, not the scratchpad; (b) `std::filesystem::status(p, ec)` returns not_found AND sets ec on MinGW, so test the returned type before `!ec` (a file-missing check silently became "unreadable" and netcode_test caught it); (c) a pointer returned by BanList Match/Find* dangles after Add/Remove (vector realloc): copy fields before the next mutation, also inside a single Check(...) argument list.
- 2026-10-29 (3 times, also hook.cpp): an owner edit of CMakeLists.txt made from an older copy silently rolled back the new-UI embed (back to docs/archive/web-legacy), crypt32, the launcher-assets copy and the GAGE_API_BASE/GAGE_TEST_SERVER cache options; the build only failed on crypt32 -> after anyone else touches CMakeLists.txt, grep it for `launcher-ui/dist`, `crypt32`, `launcher-assets` and `GAGE_TEST_SERVER` before building, and check that the "Embedded N bytes of UI" line matches the size of apps/launcher-ui/dist/index.html.
- 2026-10-30: the live-test GTA V is a non-store **Legacy disk/repack copy at `D:\Grand Theft Auto V Legacy\`** with both `PlayGTAV.exe` and a **stray `steam_api64.dll`**, owned by no store (steam library=0, rockstar registry=none). `DetectStore` (apps/launcher/game_launch.cpp) checked `steam_api64.dll` before `PlayGTAV.exe`, so it routed the launch through Steam (`steam.exe -applaunch 271590`) and forced a Steam prompt even with the right path set -> fixed by preferring `PlayGTAV.exe` (the universal Rockstar/retail bootstrapper) over a stray `steam_api64.dll` when no store record names the folder (regression case in game_launch_test, now 26). If `PlayGTAV.exe -nobattleye` itself hits a Social Club wall or no-ops on this copy, the next step is a "launch GTA5.exe directly" option (BRIDGE.md currently forbids direct launch).
- 2026-10-29: the engine's Present detour hung GTA after 1 frame because the hand-written x86 length decoder (hook.cpp decIns) read the opcode byte as ModRM (`48 89 5C 24 10` = 6 bytes, `55` failed), so the trampoline jumped back mid-instruction; passive/probe-only modes loaded fine -> any inline-hook change gets two local proofs before a live run: decIns lengths against known encodings, and a D3D11 app that detours its own dxgi Present and presents 120 frames (scratch tests: declen_test / present_test include engine/hook.cpp with -I apps -I libs).
- 2026-10-31: the BE-free launch shim redirected the BattlEye wrapper by a HARD-CODED Legacy name (`game_launch.cpp` wrote `shim_redirect_from=GTA5_BE.exe`; the shim exact-matched it), so on **Enhanced** PlayGTAV's spawn of `GTA5_Enhanced_BE.exe` slipped past, BattlEye armed, and the engine correctly refused ("BattlEye is running") before the loader could run — on a friend's Steam Enhanced copy -> the shim now matches the wrapper by SHAPE `GTA*_BE.exe` (mirrors `IsBattlEyeImage`; covers GTA5_BE.exe / GTA5_Enhanced_BE.exe / GTAV_Enhanced_BE.exe), `shim_redirect_from` is an optional off-shape override only (default empty, overwritten every launch). Keep every store/game/launcher path shape- or record-driven, never a fixed edition name. Proof: launch_shim_test shape cases. Shipped 0.2.7. **(0.2.8)** The shim ride still armed BE on **Steam Enhanced**: launching PlayGTAV ourselves on a Steam copy makes it re-launch THROUGH Steam, which spawns the wrapper in a process the shim is not in. Each store disables BE its OWN way (-nobattleye works on Enhanced but per-store) -> route by store in `DoLaunch`: Steam => `StartThroughStore`/`StartSteam` (`steam -applaunch <id> -nobattleye`, Steam forwards it); Epic/Rockstar/standalone-disk => the shim ride (proven on Epic, also injects the Rockstar `Launcher.exe`). `shim_launch=0` forces store launch everywhere. If Steam's -applaunch forwarding proves unreliable on a copy, the fallback is `-nobattleye` in `<gamedir>\commandline.txt` (game reads it directly, store-independent).
- 2026-11-02: restoring a mutant with `cp -p` from a backup kept the backup's OLDER mtime, so ninja skipped the rebuild and the suite still ran the mutant (306 -> 305 "failure" on the restored code) -> after restoring a file, `touch` it (or copy without -p) before rebuilding, and confirm the restored suite is green again.

- 2026-11-03: on resume after a context compaction, the session summary presented folder-mode (loose pack, OPEN nested vehicles.rpf) as an UNTESTED next step, but memory/content-streaming-route.md already recorded it live-tested + CRASHED (retail INT3 on the nested OPEN rpf at GTA5.exe+0x136af5b) on 2026-11-02; I acted on the stale summary and had GI reproduce the known crash (wasted a run) -> on any resume/compaction, READ the relevant project memory file (content-streaming-route.md for the jesko/content work) BEFORE acting on the session summary: the summary can be stale, the memory is the source of truth.
- 2026-11-03: an Epic player's game showed GTA's own intro instead of our loading screen (gage.log "no frame in the last 10 s (1 in total)", Present prologue `e9 ...` at install): RivaTuner (RTSS) patches dxgi Present's code and re-asserts it (restore, call the original, re-patch), so our inline E9 on the same bytes ran one frame and was overwritten; turning RTSS off fixed it -> never fight overlays over code they patch: hook the swap chain vtable slot and chain beneath (present_hook.cpp; `present_mode=0` is the old hook). Any hook on shared overlay-patched code gets a hostile re-asserting-hooker test whose OLD path must fail first (present_hook_test: inline ticked 1 of 10, vtable 50 of 50). To diagnose "engine never ticks": read the `Present prologue` line and the process list (RTSS/Afterburner/Discord) before touching the engine.

- 2026-11-03: twice in one round (T3/T4 tests, and Sync C's server_test) a local variable named `near` or `far` built fine on the native Linux server tree and broke the mingw Windows tree, because windef.h `#define`s both to nothing -> never name identifiers `near`/`far` (or `min`/`max`/`small`) in code that is also built for Windows, and build BOTH trees (build/win and build/server) before calling a test change done.
- 2026-11-03: a new selftest exe not listed in tools/deploy/wine-selftests.list fails the VPS client build ("unclassified"), and a `gate` test that reads a source file by absolute path breaks it on a moved checkout -> every new exe gets a line in the list (soft until it has passed twice on the VPS), and file-reading guards stay soft.
- 2026-11-03: a test scenario that flips a direction must flip where the speed dips (the old "reversal" row flipped at full speed = an unphysical 9 m/s step, so its 20 % skate figure was an artefact), and a sticky game flag (a damage event) that is read only inside a window must also be cleared when the window opens.

- 2026-11-04 (R3 T5): round 2's two-machine simulation stamped samples at their TRUE time ("SampleClock is idealised") while the real SampleClock stamps sample time + the fastest uplink and the NetClock baseline hides the fastest downlink; the idealised model silently removed half the latency a near car is drawn behind its owner, so "PresentLead closes the delay" looked sufficient in every test and GI still saw 2-3 m at 25 m/s -> a simulation of a time pipeline must reproduce the REAL stamp semantics of every hop (read what the clock estimator absorbs: a min-filtered offset absorbs the minimum latency), and a "model assumption" in a sim header is a live-test question, not a footnote. Also: a counter without a SIZE ("58 delay rises") cannot tell ripple from flapping; log count, mean and largest together.
- 2026-11-04 (R3 T5): ParseNearby read GET_PED_NEARBY_PEDS' slot 0 as the count; scripts' idiom is `arr[0] = capacity; n = native(...)`, the native RETURNS the count and leaves slot 0 alone, so the live `near[peds=64 vehs=64]` was the capacity echoed back (63 zero "handles" dropped as invalid by PlanSweep, so nothing wrong was deleted, but the numbers lied) -> when a native's output layout is a guess, log the breakdown that would distinguish the layouts (seen / exempt / invalid / capacity-echo) the first time, and treat a result that equals the capacity you passed in as "unknown", never as data.
- 2026-11-04 (R3 T5): a new server->client message sent on the unreliable STATE channel was dropped without a trace by the client: `ClientSession::HandleReceive` accepts a message only on the channel `ChannelFor(type)` names (the state-channel list is explicit, everything else must be reliable), so LinkInfo reached the server's send counter (10) and no client (0 events) until netcode_test's end-to-end check caught it -> every new message type needs its row in BOTH `ChannelFor` (client) and the server's receive switch, and its first test must go through the real server and the real session, not the codec alone.
