## 0. netcode_test flake (commit b1e328a)
- **Root cause:** `StateTests` creates a second rig (`rig30`) inside the lifetime of the outer `rig` (probes a, b, c). Every `Pump` in the 30 Hz block stepped only `rig30`, so for about 2.3 s idle (up to 3.8 s under load) the outer server and its probes were not polled. Server-side ENet timeouts are 400..1000 ms, and a reliable ping in flight for 1000 ms drops the peer on resume; a, b, c connected together so they drop together (players 3, joined 0 = the exact two failing checks).
- **Fix (tests only):** `Rig::companions` (other rigs serviced by every `Step()`), `Rig::Service()` split out, and `rig30.companions.push_back(&rig)` in the 30 Hz block. `tests/netrig.h`, `tests/netcode_test.cpp`. Real server timeouts untouched.
- **Proof:** the flake did not reproduce naturally on Linux (15 partial runs and 3 full runs under 3 niced busy loops all passed). Forced repro on the old harness: a mutant that leaves a reliable in flight before the `rig30` block produced exactly the two reported failures (`inv 0, mal 0, neverFar 1`; `joined 0, players 3`); with the fix both pass. 10 consecutive runs after the fix, all 196/196, per-run seconds 73.60 73.71 73.71 73.54 73.55 73.50 73.50 73.63 73.49 73.50. I re-ran it myself on the merged tree several times (73.5 s).
- **Unverified:** the PC's own failure rate (Windows `Sleep(1)` granularity widens the window; that part is inference).
- **Suggestion for lessons.md (not added):** a test that nests a second Rig must list the outer rig in `companions`; an unserviced rig is dropped after about 1 s.

## 4. Update ping, UDP query v2 (commit 07370bb)
- **Changes (20 files):** `libs/protocol/query.{h,cpp}`, `libs/net/{serverfinder.h,serverquery.cpp}`, `apps/server/{config.cpp,config.h,server.cpp,server.h}`, `apps/launcher/{version_gate.h,gage_gui.cpp,BRIDGE.md}`, `tools/deploy/release.sh`, tests (`server_test`, `serverquery_test`, `version_gate_test`), docs (`docs/api/protocol.md`, `docs/api/server.md`, `docs/UPDATES.md`, `docs/OPS.md`, `apps/master/PROTOCOL.md`).
- **Wire (little-endian, all datagrams exactly 24 bytes):** request v1 and v2: 0..3 "GAGE", 4 kind 0x01, 5 query version 1, 6..7 u16 reply version wanted (v1 askers write 0; exactly 2 asks for v2, any other value gets v1), 8..15 nonce, 16..23 zero. Reply v1 unchanged byte for byte: 5 = 1, 6..7 protocol, 8..15 nonce, 16..17 players, 18..19 maxPlayers, 20..23 zero. Reply v2 (only when asked): 5 = 2, 20/21/22 = latest client major/minor/patch, 23 = 0. Asserted vectors: request v2 `474147450101020001020304050607080000000000000000`, reply v2 for latest 0.4.4 `474147458102010001020304050607080300200000040400`. A request of 23 or 25 bytes or with byte 5 = 2 is not a query (no reply); junk in 6..7 selects v1; a v2 reply is never sent unasked.
- **Deviation 1:** the v2 request keeps byte 5 = 1 and asks in the u16 at 6 (the field v1 already specified as "zero, ignored on receipt"). A literal byte 5 = 2 request is not a query to a 0.4.2/0.4.3 server, so a new launcher would get silence and show the server offline; with this encoding an old server answers v1 in one round trip and the launcher reads "latest unknown".
- **Deviation 2:** the version reaches the server through `GAGE_LATEST_CLIENT_VERSION` in `/etc/gage/server.env`, not a new `server.json` key. I verified in the code (`apps/server/config.cpp`) that an unknown key is fatal at start in an old server binary, so a `server.json` key would break the rollback in `deploy-server.sh`; the unit's ExecStart is fixed. The server still reads a `latestClientVersion` key in `server.json` if present (it wins over the env var); malformed -> config error; absent = 0.0.0 = unknown. `server.json.example` deliberately does not list it. `release.sh` step 3b (`set_latest_client_env`) runs after the client is published and before the countdown, replacing or appending exactly one line and keeping owner, mode and inode; a failure is a warning, not a stop; it also warns if `server.json` itself has the key.
