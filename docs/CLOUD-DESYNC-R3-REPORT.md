## 1. Health stuck at 50 % (T1)
**Cause.** Measured live: `Welcome.playerHealth 200 -> max 300`; `SET_ENTITY_MAX_HEALTH(ped 514, 300) read back 300; ped health 200`; every 10 s for 10+ minutes `ped 200 / max 300, server health 195 of 200, bar 50%, reconciles 12 (gave up 4)`. GTA caps the player ped's health somewhere other than the entity maximum; round 2's `SimPed` MODELLED health above 200 being accepted once the max is raised, and the log contradicts it. Which native or rule does the capping is **unknown** (no log shows the health after each write).
**Fix.** A measured-ceiling probe at session start, after a ped swap and after a respawn (SET_ENTITY_MAX_HEALTH, SET_ENTITY_HEALTH, SET_PED_MAX_HEALTH, SET_ENTITY_HEALTH again, a read after each step, one frame later and 1 s later) classifies the behaviour (holds / cap follows SET_PED_MAX_HEALTH / capped / unknown) and picks a mode: **DIRECT** (GTA holds 100+ph: the 0.4.7 behaviour) or **SCALED** (the ped's GTA health = 100 + max(1, round(hp * C / ph)) with C the measured ceiling, never above it and never on the death line for a living player; the HUD bar and death are driven by the SERVER number; environmental damage the tracker sees in GTA units is scaled back by ph / C; recovery is by applying g(newServerHp), no delta accumulation). A reconcile give-up or an unprobed ped handle triggers one more probe instead of fighting the clamp. Why this design instead of lowering `playerHealth` on the VPS (changes time-to-kill for everyone to work around a client limit, and does nothing if the cap is below 200) or relying on SET_PED_MAX_HEALTH alone (it is part of the probe; the log shows the max natives did not move the cap, and nothing guarantees a second native will).
**Failing-on-old.** `health_mode=direct` is the 0.4.7 behaviour; `tests/r3_t1_health_tests.h` (33) + `t6_health_tests.h` (SimPed rewritten as five switchable models: Direct, Cap200 = the live behaviour, FollowsPedMax, CapNextFrame, Cap150; every scenario under EACH model) reproduce the live state on the old behaviour (`ped 200/max 300/server 195/bar 50 %, reconciles 12, gave up 4`) and show `SCALED, ceiling 100, ped 198 on max 200, bar 97.5 %, 0 reconciles, 0 self-hits` on the new. Mutants: always DIRECT (72 of 604 fail), loss not scaled back (20), ToGta can return 0 (3), no re-probe on give-up (4), no probe for an unprobed handle (2), probe skips SET_PED_MAX_HEALTH (16), take-back detection removed (17), bar ignores in-flight damage (1), SetScale does not re-apply (1), tracker not held during the probe tick (survived, test added, 1). I did not re-run the new tests against the pre-fix commit (they use the new API).
**Live steps.** Join the VPS and grep `gage.log`: `engine: health: Welcome.playerHealth 200 ... health_mode=auto`; THE line: `engine: health: probe [session start] ped N, playerHealth 200 -> wish max 300 ...: start ...; SET_ENTITY_MAX_HEALTH(300) ok -> ...; SET_ENTITY_HEALTH(300) ok -> ...; SET_PED_MAX_HEALTH(300) ok -> ...; SET_ENTITY_HEALTH(300) ok -> ...; => <verdict>; ceiling C; mode SCALED|DIRECT` (verdicts "GTA holds the health", "the cap follows SET_PED_MAX_HEALTH", "HEALTH CAPPED below the wish whatever the maxima read"); then `probe +1 frame` ("GTA TOOK IT BACK") and `probe +1 s`; every 10 s `engine: health: mode ..., measured ceiling C, ped H / max M, server health S of P, bar B%`. Healthy under the live behaviour: SCALED, ceiling 100, bar = server/200 (97-98 % at 195), reconciles 0. Manual: shoot or fall (bar drops proportionally), `/heal`, die and respawn, reconnect: each ends at a full bar. **Switch:** `health_mode=direct|scaled|auto` (HKCU\Software\GAGE-MP, read at Welcome).
**Weak.** All GTA behaviour is modelled. A GTA that drops BOTH probe writes (ped in transition) reads as a cap and runs SCALED at lower resolution (harmless for bar and death). In SCALED a real puppet bullet that hurts the local ped weighs ph/C more server hp per unit (the existing puppet-grace is the only protection). A 12/4 in the new log with `mode SCALED` is NOT the old bug (3 re-probes = 4 episodes of 3 writes). The probe briefly writes up to 355 on the ped. The server still accepts any self-hit with no cap. `SetPlayerMaxArmour` is wrapped but unused. Engine wiring is compiled only.

## 4. Vehicle damage state (T4)
**Cause of the two suspect reads.** `199 of 199 smashed windows` (measured live; mechanism simulated): `ReadVisual` called `IS_VEHICLE_WINDOW_INTACT` for slots 0..7 whatever glass the model has and set a bit for every "not intact", with no baseline, so any slot that reads "not intact" for any reason (a slot the model lacks, a window rolled down, a read that never changes) was "smashed" in every update; the copy then smashed it on someone else's clean car (`copies show window damage 1`). The log does not contain the mask, so which slots are junk is unknown (the new line prints them). Tyres share the path. `96 and 96`: structural, not a wrong read: `ClassifyBrake` makes brake lights a superset of handbrake (checked over 20000 random pedal states), so equal counts only mean the foot brake never acted while rolling; a still car is sent at 5 Hz, so 96 updates is ~19 s of a parked car with the handbrake held (plausibly real and harmless); control ids 71/72/76 are the standard INPUT_VEH_* ids and nothing points to a wrong id; a 10 s pedal histogram settles it from one log.
**Fix.** SANITY LAYER (`libs/sync/vehicle_damage.h`): per-slot baseline at the first read: a bit set at the first sample while the server shows none is an *unreliable slot* (counted, logged once per car, never sent, masked out of the copy's own readback so the copy cannot fix, smash or report it as a Hit); a real change needs 2 consecutive reads or a corroborating signal (body health fell within 3 s, local player shot lately); `PedalGuard` withholds a handbrake held at the first sample of a car rolling above 3 m/s or held 2 s at 5+ m/s without slowing (a parked handbrake is believed); `HandbrakeLimiter` on copies (honoured on a standing car, at most 4 s while rolling); a SERVER rule (`damageNeedsHealthLoss`, `cleanHealth` 995) refuses a report that adds a window / damage-block rise / lower petrol tank while body health is >= 995 (Hit-set bits exempt; also protects against an old-build controller). DAMAGE STATE (v7 block): petrol tank health (`u8` = health/4), broken doors (6 bits) and left/right headlight (2 bits), up to 8 dent probes (`dentMask` + a byte per dented probe, 2 mm steps); controller `DamageReporter` (500 ms, 250 ms while health falls) believes a rise only with server agreement, a body-health fall or a held second read; send policy: the block rides 6 updates after a change then every 3 s while the server lacks it, nothing when equal to the server's; server merge is monotonic (petrol min, parts OR, dent max; `RepairDamage()` hook for later); copy `DamageApplier`: doors with `SET_VEHICLE_DOOR_BROKEN` (delete=true), petrol with `SET_VEHICLE_PETROL_TANK_HEALTH`, headlights via a small `SET_VEHICLE_DAMAGE` at the lamp escalating 120/240/480/960 until the read-back says broken (no setter exists), dents via `SET_VEHICLE_DAMAGE` at the probe in a closed read-back loop (aims at 40 % of the missing depth, learns the damage-per-metre gain, then 90 %, at most 4 rounds per probe; a replay that does nothing stops after 4 tries; a clean server block costs zero native calls); copies are made unable to damage themselves (`CAN_BE_VISIBLY_DAMAGED=false`, `ENGINE_CAN_DEGRADE=false`, petrol tank damage disabled; the visible-damage flag is lifted only inside a replay; a controlled car gets the defaults back). Dents are STATE read off the controller's hull rather than replayed `VehicleImpact` events, because VehicleImpact reaches only the two controllers (never observers) and misses walls, props and rollovers, and state survives packet loss. The controller adopts the server's lower body/engine health (> 25 below its own), so a shooter's vehicle Hit shows on the car.
**Failing-on-old.** `tests/r3_t4_tests.h` (51, in `t3_vehvisual_test`: 42 -> 93): A1 (junk window slot masks C0/30/FF/01: the OLD chain reports 199 of 199 updates with a smashed window and smashes it on a clean copy; the new layer 0), A1b (tyres 100 of 100 old, 0 new), A2 (96/96 reproduced, 126/96 once the foot brake is added), F2a (the v6 chain end to end smashes windows on the copy) vs F2b (v7 does not); a test with natives that return "damaged" for slots the car lacks (A1, B5, E2: junk windows, tyres, doors, dents, petrol). 12 mutants all caught (no baseline 12, PedalGuard never stuck 2, not-slowing rule removed 1, server rule off 3, reporter rise needs no corroboration 1, first-read dents not flagged 1, applier no round limit 1 (240 calls in 120 s), encoder drops the block 6, limiter never suppresses 1, petrol assigned not min-merged 2, learned gain unused 1, VisualGuard no-op 6). Closed-loop convergence: a dent reaches 60 steps in at most 4 replays for a game 0.25x..2x as strong as the first guess; a 6x game overshoots once to 144 steps and stops.
**Live steps.** Needs the lockstep 0.4.8 build. `engine: vehicle damage (R3 T4), last 10 s:` (switches, controller reads and blocks sent, unreliable slots, the pedal histogram, the copy's replays / converged / no-effect / gave-up / learned gain); `engine: vehicle id=N damage (ctl|copy):` (the controller's reads next to the copy's server block and local read, per damaged car); `engine: vehicle id=N sanity:` (slots flagged unreliable, stuck handbrake); first replays `damage (copy): server petrol`; `engine: vehicle: model 0x... dent probe frame`. **Weak.** Everything below the wire is unverified on the real game: `GET_VEHICLE_DEFORMATION_AT_POS` / `SET_VEHICLE_DAMAGE` semantics (local-frame offsets, length in metres, damage/radius/focus mapping) are assumed; a stronger game overshoots once and a dent cannot be undone; `SET_VEHICLE_CAN_BE_VISIBLY_DAMAGED(false)` may also block `SET_VEHICLE_DAMAGE` (each replay is bracketed true / replay / false, the read-back shows whether it took); the 8-point probe frame is a guess (roofs and rollovers uncovered; the hull comes from the wheel bones, fallback 0.95 / 2.2 / -2.2); **fire is not carried** (engine/tank health below 0 is clamped to 0 on the wire; a copy driven into the burning range would burn on its own timeline, judged worse than not showing fire); **repair never propagates** (monotonic, nothing calls `RepairDamage` yet); the server's clean-car rule refuses a script-smashed window with no health loss (no such path exists today; threshold 995). ## 5. Car collisions and car position (T5)
**Cause (simulated, consistent with GI's log).** The 2-3 m is **not** the 84 ms shared delay: round 2's `PresentLead` is applied (the `!iControl` path passes `&v.lead`, `dispT` is valid, the 250 ms cap is not reached at 84 ms) and closes the render delay, but not the network latency no timestamp carries: the server's `SampleClock` stamps a vehicle sample at its sample time plus the controller's fastest uplink, and the `NetClock` baseline (minimum offset) hides our fastest downlink, so "now on the timeline" is half the controller's round trip plus half ours behind the owner's real position. One-car sim with the real stamp (`NetCfg::stampBias`, live rhythm 601 frames/10 s, clean link): 40 ms each way leaves **2.05 m at 25 m/s** (3.27 m at 40 m/s) on round 2's code.
