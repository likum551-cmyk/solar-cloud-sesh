## 1. Walking (Task 1, branch `cloud/desync-r4-t1-blend`)
**Cause.** Measured live (0.4.9): velocity pushes up to 30.7-33.6 m/s, pose-ped error 6.0-7.8 m, puppet 1.3-2x too fast, 11-40 "contaminated velocity reads" per 10 s. Mechanism read from the code and reproduced in the sim: the 0.4.9 push is `GET_ENTITY_VELOCITY read + correction`; only the correction is capped (`residualMaxMs`, 2 m/s), so with a task that runs faster than the pose and a write only partly honoured the read is the task's velocity and the push cannot slow the ped by more than 2 m/s; the error grows until the persistent-error snap (`offLimitMs`) teleports it. Sim of 0.4.9 ("task 1.5x fast, half-honoured writes"): 2 hard snaps in 20 s, 6 in a sprint, p95 3.4-4.0 m, speed 1.06x / 1.20x the pose; writes ignored and a 2x task: 12 snaps, 1.7x. **Not reproduced:** the 30 m/s peak itself appears only if the read spikes (an assumption). "move 3 / move 4" is not a blend ratio: it is the sender's `PedState.move` (0..3 gait, `kMoveInVehicle` = 4); the ratio the controller sends is 1..3 and a test asserts max 3.00.

**Fix (`LocoMode::Blend`, baked default; evidence: simulated + compiled).** FiveM-style: velocity = low-passed pose velocity + clamp(error / 0.25 s, 2.5), hard ceiling `|v - pose velocity| <= 3.0`; z left to the game unless the pose is more than 0.5 m off; **no coordinate writes except a snap beyond 6 m / a real teleport** (the persistent-error snap is off in Blend). Gait animation source (decided from what the code proves): the straight task to a far point on the pose's line, as the **gait source only**; position is carried by velocity writes. Rejected: a `TASK_PLAY_ANIM` walk loop (only upper-body 16|32 clips are proven to play, no verified walk/run clip name, no way to set the clip rate: `SET_ENTITY_ANIM_SPEED` is not in hook.h) and a task whose target is the ped itself (arrives at once, gives no gait). The move blend ratio is a continuous knob 0.5-3.0 trimmed by the mean correction, so a task running 1.5x/2x too fast is slowed to about 1.0x when the writes are partly honoured (a gait that is too fast is answered by a LOWER ratio, not a stronger push). A moving gait holds >= 400 ms; stall re-issues limited to 3, then `NoGaitSource` (retry every 15 s). Self-check `BlendWatch` compares the ped's velocity and positions with the velocity written the frame before (>1 m/s = a "fight" frame) and degrades to the rigid follow (`LocoLevel::Placed`) when the error is over 1.2 m and not closing for 1 s, over 0.7 m with >75 % fight frames for 0.5 s, or in a snap storm. The rigid follow's step is now capped at pose speed + 3 m/s with pose-velocity feed-forward (the old Placed stepped 8 m/s regardless). Two puppets finding it within 60 s impose it on all for 45 s. The baked default is one tri-state (`kBakedLocoMode`: anchor | straight | blend, default blend); `loco_push` is ignored by Blend.
`LocoInput::swingActive` (Task 3's interface, honoured in ALL modes): holds every task issue and repair while set, plus 700 ms after (`swingHoldMs`), because `swingProbe.Active()` can fall while a clip plays on; the velocity drive and the snap continue. Wired in DrivePeer as `in.swingActive = pe.swingProbe.Active()`.

**Fails-on-old proof.** The new acceptance (p95 <= 0.5 m, max <= 1.5 m outside a teleport, speed within 10 %, push <= pose + 3, zero hard snaps, no gait held < 400 ms) was run on the 0.4.9 behaviour first. Over 132 runs (12 model cells x 11 scenarios: walk/run/sprint straight, gait changes, 90-degree turns, run/stop, circle, 1 s and 5 s outages, teleport, ramp and curb; 30 Hz feed, 80 ms jitter, 2 % loss; also at 30 and 144 fps), 0.4.9 fails 117 and makes 629 hard snaps. Worst cells: B1.5/C p95 3.97 m max 5.00 m, 22 snaps; B2/E p95 5.19 m, 121 snaps; A/E max 7.58 m, 178 snaps. Models: gait source A none, B 1.5x/2x too fast (rate cannot scale it), S scaled; velocity D honoured, C 50 % overwritten by the task, E ignored (plus read lies / spikes). **Blend:** D cells all pass (p95 0.26, max 0.32); C cells p95 0.47-0.50, max 0.68-1.47 (B1.5/C touches exactly 0.50; the test bound is 0.55 because the stop scenario sits at 0.50-0.51), some runs fall to the rigid follow; E cells and A/C: rigid follow after about 1.4 s, worst p95 0.66, no hard snap; speed from positions 1.00x on every straight run; largest push above the pose exactly 3.00 m/s. 19 source mutants, all caught (e.g. ceiling removed 6 failures, base = ped's read 8, snap at 2 m 7, trim off 7, self-check off 8).

**Live steps for GI.** Join the VPS with two players, walk / run / sprint / stop / U-turn for 60 s, grep `gage.log`:
1. Welcome: `engine: remote on-foot walking via BLEND ... (loco_mode, build default)`.
2. Per puppet every 10 s: `engine: loco slide id=... | R4 T1: mode blend, speed from positions X vs pose Y m/s (ratio), largest per-frame correction ..., hard snaps N, pose-ped error p50 .. p95 .. max .., ... verdict: ...`.
3. `engine: gait id=... ; R4 T1 <verdict>` and `engine: loco level id=...` (once, if it fell to the rigid follow).
Healthy: ratio 0.95-1.05, correction <= 3.0, hard snaps 0, error p95 <= 0.5 m, max <= 1.5 m, verdict `blend ok`. `blend fighting the task: N frames ...` with a stable error = writes only partly honoured, the trim carries it. `blend DEGRADED` = writes not honoured on that build, the error stays small through the rigid follow; then try `loco_mode=anchor`. `gait source NONE` = the task shows no gait (model A); position is still carried. **Rollback** (HKCU\Software\GAGE-MP): `loco_mode=straight` (0.4.9), `loco_mode=anchor` (0.4.8), `loco_push=nudge|velocity` (anchor/straight only), `loco_selfcheck=0`, `loco_r3=0`, `loco_repair=0`.

**Weak points.** All GTA behaviour is a model; whether `SET_PED_DESIRED_MOVE_BLEND_RATIO` changes the speed of a RUNNING task and whether a fractional ratio is honoured by `TASK_GO_STRAIGHT_TO_COORD` are unverified (the sim axis `mbrLive` exists but the matrix runs with it true). When the writes ARE fully honoured (B/D) the clip plays at 1.5-2x the pose speed while the position is exact: a documented limit (a test asserts it); a quiet probe is the candidate next step, not built. Sharp turns in C worlds reach p95 0.47-0.50 m / max 1.47 m (B2/C), near the bound. The trim is a pure integrator and oscillates where writes are ignored (hidden by the fast fall to the rigid follow, so the first 1-1.5 s of motion in such a world shows a 1-2 m excursion, and the rigid follow is coordinate writes, which may cancel the walk: the R3 "W" hypothesis). No shared learned trim across puppets. Thresholds untuned (nominal speeds 1.5/4.5/7, fail error 1.2 m, fight 1 m/s, snap 6 m). Engine glue (verdict wording, z handling, `LocoDiagFrame` fields) is compiled only. The R3 melee rung `TASK_PUT_PED_DIRECTLY_INTO_MELEE` needs the anchor, which exists only in `loco_mode=anchor`; with the Blend default that rung is skipped (as it already was for straight).

## 2. Car to car collision (Task 2, branch `cloud/desync-r4-t2-collision`)
**What the live number measures** (code reading plus a sim twin; spec in `docs/sync-specs/vehicle-collision-authority.md`). "Drawn vs the owner's report now" = the entity's position before the frame's commands against the owner's snapshots extrapolated by the same interpolator to NearT + link lag. It is lag-compensated with the same lag the aim uses, so it is **blind to a wrong link lag** (in the sim a 30 ms lag error is 0.41-0.49 m of real error at 15 m/s and 0.00 m of metric) and **blind to extrapolation error** (both sides use the same dead reckoning). It is therefore not a measure of true display error. The lead falling to 104 ms over 30 m/s is arithmetic (speed bands mix distances: lead full within 40 m, zero beyond 70 m; the sim gives an all-distance lead of 82 ms against 180 ms within 40 m), not a cap. 905 of 980 frames extrapolating is by design (the near clock draws a copy 100-200 ms past its newest snapshot). The position line now prints the in-range numbers `[within 40 m: N frames, aim X ms behind, lead Y ms]`.

**Baseline (round-3 logic, simulated)**, two-machine sim with the real stamp semantics (SampleClock stamps sample time + the fastest uplink; NetClock hides the fastest downlink), RTT 92 ms, jitter 15 ms, 30 Hz, 8 seeds; mean divergence in metres between A's view and B's view of each car, car A / car B:

| scene | base +1 s | base +2 s | new +1 s | new +2 s |
|---|---|---|---|---|
| head-on 15+15 | 0.03 / 0.03 | 0.03 / 0.02 | 0.03 / 0.03 | 0.03 / 0.03 |
| side-swipe 20 | 0.64 / 0.72 | 0.65 / 0.71 | 0.11 / 0.18 | 0.03 / 0.07 |
| rear-end 25 | 0.56 / 0.64 | 0.65 / 0.64 | 0.13 / 0.13 | 0.03 / 0.03 |
| stationary hit 15 | 0.60 / 0.61 | 0.03 / 0.03 | 0.09 / 0.10 | 0.03 / 0.03 |

Head-on with both cars braking from 18 m: divergence at contact 0.62 m base, 0.14 m new. The base fails the 0.5 m target at +2 s in the side-swipe and the rear-end. Full tables for all four game models are in the spec, section 4.

**Cause 1 (simulated, traced step by step): stale velocity feed-forward.** The near clock draws a copy L = 100-200 ms past its newest snapshot; the drive controller adds a proportional correction to that stale target velocity; for a braking car it settles at e = a*L/g, about 0.5-0.65 m at a = 9 m/s^2, L = 0.2 s. It scales with RTT (0.37 m at 20 ms, 0.65 m at 92 ms), is unaffected by jitter/grace/adoption/arbiter, and persists until the cars stand still: exactly when a crash is judged. **Cause 2 (simulated, hypothesis for the live game): world touches open a soft grace** (400 ms, weight 0.15 rising, no angular correction before 0.5); the copy then drifts off its owner (model 2: worst seed 2.9 m at +2 s after a head-on; 0.28 m with the gate on). **The arbiter's 15.6 m/s** (code and arithmetic, not log evidence): the change of velocity depends on closing speed and masses only, not on the approach distance; two equal cars at 25 m/s closing get 15.62 m/s each, a bike (250 kg) into a truck (7 t) gets that at 13 m/s. So 15.6 m/s is consistent with a real head-on; "from a 1.4 m approach" was a misreading. The arbiter code is unchanged. **Not reproduced:** GI's 1.4-1.8 m mean tracking error under 15 m (the clean sim stays at 0.15 m or less): a cause that is not in the model is at work live; the 37-degree heading errors probably come from extrapolating a collision/spin yaw rate over 150 ms (unmeasured, unaddressed).

**Fix (simulated; no wire change).** `VehicleInterpolator` extrapolates with the tangential acceleration (estimated from the speed change over >= 90 ms, clamped to +-10 m/s^2, a step faster than 14 m/s^2 is treated as a collision and counts 0, a braking car stops and never reverses; position and velocity both corrected). `VehicleDriveInput.ownNear` gates the flag / speed-loss / kick triggers: a flag with no car we control within `kContactNearM` = 10 m is a world touch and no longer opens a grace. New `ContactWatch` (`libs/sync/vehicle_position.h`) compares a copy with its owner at +0.5 / +1 / +2 s after **every** contact, applied server impact, adoption and ignored world touch (8 slots, merges events on a watched copy, skips a check read > 300 ms late). `ClassifyTouch`/`TouchTally` split a flag edge into a car we control / another copy / in the air / something solid / ground. Server: a per-impact log line `contact: impact #N vehicle A (class, ctrl) with vehicle B ...: closing X m/s, normal, depth, dv A, dv B` (8 per 10 s). Rollbacks: `veh_contact_gate=0`, `veh_accel_extrap=0`; unchanged `impact_sync`, `veh_prox_contact`, `veh_near_clock`, `contactLagCapMs`.

**Fails-on-old proof.** Each new check asserts the base side with the `Baseline` / `accelExtrap=false` / `ownNearM=0` switches inside the same binary. 13 mutants (acceleration estimate off 6 failures, gate ignored 4, hit-rejection removed 3, velocity not scaled 4, stop clamps 2 and 1, watch rules 2/1/1, touch order/threshold 1/1) all caught; the first run exposed two weak fixtures (stop clamp sat in Holding mode, a touch-order case missing), fixed.

**Live steps for GI.** Deploy client + server (the server change is a log line). On BOTH machines at the same moment, grep: `engine: vehicle contacts (R4 T2)` (what the flag touched, edges the gate ignored, closest copy to our car, the server impact's authoritative change / closing / depth, and `copy vs the owner after a contact: ... +0.5 s: N compared mean X max Y ...`); the per-edge `collision flag rose on the remote copy: touched ...` lines; `engine: vehicle position (R3 T5)` with the new `[within 40 m: ...]`; server `contact: impact #...`. Reading: mean <= 0.5 m at +1 s and +2 s = converged; several metres = the game does something the model does not.

**Weak points.** Everything is simulated: the planar physics, copies honouring a velocity command, the world-flag model. The gate is a 10 m origin-to-origin distance heuristic (a copy touching a ped we control is not softened). The estimate is tangential only; yaw-rate extrapolation unchanged. Mass classes disagree (server: model-name table; client proximity predictor: vehicle class), not fixed. Not covered: T-bone scene (chaotic in the planar model), no server_test for the new log line. The sim cannot show whether the friend's machine applied his half of an impact.

## 3. Punches (Task 3, branch `cloud/desync-r4-t3-punch`)
**Which symptoms Task 1 alone should resolve.** Hits (0 server-confirmed in 0.4.9, 8 in 0.4.8): expected to improve a lot once puppets stay within about 1 m of their owners; also the "windows opened on a puppet 0 / puppet within 3 m 0" counters if the cause was a missing or far puppet. **Not resolved by Task 1 alone: the animation** (in 0.4.8 the puppet was within 3 m, 6/6 were "playing" and GI still saw no punch). The only part of the animation question Task 1 can answer alone is the blend-out candidate: it now suppresses movement-task re-issue while a swing plays (`swingActive`, all modes).

**Hits (simulated, consistent with the logs, not proven live).** The server judges a swing against the victim's REAL track (what the friend's own client reports); GI aims at the PUPPET. Real `melee::Adjudicate`: a punch at a puppet 1.0 m in front of GI hits the friend only if the friend is within 0.9 m further away from the puppet, or about 1.6 m to the side (reach 1.4 m + 0.5 m slack, centre to centre, 65-degree cone). At the live puppet error of 6-8 m it is a miss in all 24 directions; with error 0 (the 0.4.8 geometry) it is a hit. Real server over loopback: a swing at a spot where Bob is not (really 7 m away) = `no_target`, no Damage; Bob where the puppet is = one Damage. **No server defect found** (attacker judged at press + 220 ms by his own sample clock, victim at the blow minus 100 ms, nearest living player on foot wins); the hypothesis "the Task 1 displacement made GI punch a spot where the friend was not" is consistent with 0 blows and no other cause turned up. "Swing windows opened on a puppet 0" means no puppet with a hit pool existed, or it was dead/seated: a client-side fact the new client line explains.

**Animation (cause NOT decidable offline).** "SEEN PLAYING 6/6" (measured live, 0.4.8) was the read-back of the first frame after `TASK_PLAY_ANIM`; the R3 probe stopped at the first yes and the ladder pinned the variant. Nothing checked that the clip stayed. Simulated: with a model where a locomotion task takes the plain upper-body layer off after 70 ms, the old logic reports 10/10 SEEN PLAYING and pins Upper while 0 swings were on the ped at +100/+250 ms, which fits "6/6 playing and no punch". Not excluded: the 400 ms cut of the longer INFERRED clip (`heavy_punch_a` wind-up only), the upper-body filter, the puppet being elsewhere.

**Fix (compiled + simulated).** `SwingProbe` now follows the swing: IS_ENTITY_PLAYING_ANIM sampled at +100 / +250 / +450 ms after the first sighting (plus anim current/total time when available, -1 = unknown), verdict `Progressed / BlendedOut / Flicker / Frozen / Unread`; `Active()` covers the whole swing window (460 ms for the shipped swing, 1100 ms whole clip, explicit hold for the melee task, never longer, cancelled on dead/replaced/seated ped). A blended-out swing counts as a ladder miss, so the ladder climbs by itself. A one-pass **survey** exercises more than one variant per session (registry `melee_survey`, default 1): upper-body 16|32 400 ms (shipped), upper-body whole clip, upper-body not-interruptable, full body (8) whole clip, melee task (only with an anchor, so skipped in straight/blend); the winner (highest progressed/issued, earliest on a tie) pins the ladder; a survey swing never moves the ladder. Per-swing client line and a `/swing` command (plays the next attempt on the nearest other player's puppet within 25 m, local only; the overlay names the attempt and then the read-back verdict). Per-swing line of OURS: peers known/drawn/hittable, nearest puppet distance, and "THE PUPPET IS DISPLACED" when it is > 1.5 m from its owner's pose, or "NO puppet to hit". Server: every judged swing logs a line with the miss reason and timing (30 per 10 s), e.g. `melee: Alice swing (shotSeq 1, weapon 0xA2719263) judged no_target: nearest living player on foot 7.00 m (reach 1.90 m), 0.0 degrees off the heading; why: id 1 is the nearest and stands 7.00 m away, 5.10 m beyond the reach (dz 0.0); timing: ...`. `World::GetEntityAnimTimes` is a neutral stub (returns false, calls nothing): the two natives are not in the crossmap. Rollbacks: `melee_survey=0`, `melee_follow=0`, `melee_anim=play|melee_task|off`; server `meleeReachPercent`, `meleeAdjudicate=0`.

The new tests use new APIs so the pre-fix commit does not compile them; the proof is 16 mutants, all caught (follow disabled 11 failures, verdict always Progressed 6, survey always plan 0 4, PinTo no-op 3, trailing melee entry 5, blended-out not a ladder miss 3, reach slack removed 5 (3 of them R3 tests), nearestId/byTimer/miss reason/GapMs 2/1/1/1, old logging rule: netcode 264/266). ## Interface between Task 1 and Task 3 (checked at merge)
`pe.swingProbe.Active()` is set in `PlayPeerShots` before the locomotion input is built in the same `DrivePeer` call, so `in.swingActive = pe.swingProbe.Active()` is correct for the same frame. T1 was written against the R3 probe (Active true only for the 250 ms probe window) and compensates with its 700 ms hold; T3 widened `Active()` to the whole swing window (460 / 1100 ms), so the two overlap harmlessly (the hold simply starts later). Task-issue counters in `LocoTaskCount` (engine.cpp) are the ones T3's "a locomotion task was issued meanwhile" diagnosis counts; T1 added no new task-issue counter (its `swingHeld` counts suppressed issues), so the diagnosis does not undercount. Both trees build and the full list is green with the two merged; the combination itself is untested beyond that (no test drives a Blend puppet through a real survey swing).
